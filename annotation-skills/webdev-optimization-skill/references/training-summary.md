# WebDev Optimization Training Summary

## 任务与队列

- 任务名称：WebDev 优化项目标注，手册标题为 `WebDev优化项目标注手册v3.0`。
- 作业平台：AIDP，主任务链接来自手册中的 `Webdev场景优化_0511`，任务 ID 为 `7638533926797332270`。
- 数据形态：每条任务包含 prompt 和模型生成的 Web 产物，标注时查看嵌入视窗和外部 URL。
- 常见类型：普通 Web 页面、UI 类页面、游戏类页面、动画场景、贺卡类、空白页或单一无功能页面。
- 分值：三档 `+1`、`0`、`-1`。
- 主要维度：功能完整度、功能缺陷、美观度。
- 工作流状态：当前材料已完成学习，可生成任务 skill。权限问卷原链接未在可读材料中直接给出，需在平台页面出现后再补充 quiz-draft。

## 核心判定

- `+1`：交互完全正常，三个维度都通过，UI 观感良好。0429 规则更新明确，只要所有维度都通过就可以给 +1，不要求必须有额外亮点。
- `0`：基本满足题目，但存在一两个边缘或可优化瑕疵，或者满足基本要求但没有明显提升。
- `-1`：存在严重缺陷，例如不遵从 prompt 核心要求、核心功能缺失、游戏基本不可玩、UI 滚动或布局问题明显影响体验、页面大面积异常、功能链路阻塞。
- 三个维度独立判断。某一维度可以单独给低分，不代表所有维度都要低分。
- 总分判断要以用户体验和 prompt 遵循为核心，不因单个小瑕疵过度打低，也不能忽略核心功能缺失。

## 三个维度

### 功能完整度

- 看 prompt 中明确提出的基础功能、内容、交互、主题、颜色、动画、布局和关键元素是否覆盖。
- prompt 明确要求的颜色、主题、响应式、移动端友好、动画效果、特定控件或流程都必须验证。
- 未在 prompt 中提到的通用游戏特性或扩展功能，默认不能作为不通过理由，只能作为改进建议或加分项。
- 如果 prompt 说要某个 tab、按钮、弹窗、上传、编辑、筛选、游戏玩法等，必须测试其是否实际可用。

### 功能缺陷

- 看已实现功能是否存在 bug，例如按钮无响应、链接跳转异常、图片加载失败、页面白屏、控制台报错、流程卡死、画笔无轨迹、点击位置错位、资源加载依赖特殊网络。
- 即使 prompt 没明确说按钮要跳转，只要页面设计了自然交互预期，点击无反馈也可记为功能缺陷。
- 0430 规则更新要求，白屏、单一无功能页、ready to build 等都不要直接废弃，要打开外部 URL 和控制台，将具体报错记录到功能缺陷维度。
- 控制台 error 和 warning 可作为迭代信息记录，但是否通过仍以实际体验和核心功能为准。

### 美观度

- 看布局、边距、对齐、滚动、遮挡、视觉层次、样式一致性、整体观感和主题匹配度。
- UI 类产物不死抠小细节，但整体观感、基础需求和主要交互必须过关。若存在多处或重大视觉问题，应降低美观度。
- 游戏类 UI 看得过去即可通过美观度，但若玩法界面严重变形、遮挡、不可读或影响操作，应降低。
- 美观度可以写建议，但若有明确缺陷，应先指出缺陷。

## 操作流程

1. 阅读 prompt，拆出核心功能、明确视觉要求、响应式或移动端要求、游戏/动画/UI 类型。
2. 在标注平台查看嵌入视窗，但必须点击新窗口打开产物 URL 进行完整测试。
3. 测试 prompt 明确要求的核心功能和页面自然可见控件。
4. 建议打开控制台查看 error 和 warning。白屏、ready to build、渲染异常、单一页面无功能时必须复制或概括具体报错到功能缺陷。
5. 如果 prompt 明确要求移动端友好或响应式，使用约 375px 移动端视窗验证；prompt 未提及则不强制以移动端适配减分。
6. 对游戏类，实际试玩核心玩法，判断能否基本玩、控制是否可用、失败/重开/得分等核心反馈是否合理。
7. 对动画场景，确认是否有动态效果。0515 规则明确，完全没有动效不行。
8. 分别填写功能完整度、功能缺陷、美观度和总体评价。最终提交前默认请用户确认，除非用户明确授权自动提交。

## 特殊场景

- 白屏或空白页：不走废弃，打开新窗口和控制台，记录具体报错到功能缺陷。白屏和空白页暂不结算，但标注仍需说明问题。
- ready to build：多为模型未编译完成。若有报错，复制报错到功能缺陷；若无报错，仅备注 ready to build 状态。
- 单一无功能页面：记录为特殊 case，按规则观察是否只是简单但可接受，还是没有实际功能导致低分。
- 资源需要特殊网络导致白屏：记录资源加载环境问题和白屏现象。
- 不同屏幕或视口表现差异：如果影响操作或渲染，应记录；如果 prompt 明确要求响应式，更应影响功能完整度或美观度。
- 画布、画笔、鼠标位置错位：属于功能缺陷，必要时说明设备、浏览器或视口差异。
- UI 批次里出现游戏模拟器等任务：按 prompt 核心需求判断，不只按批次名称判断。

## 游戏类判定

- 游戏核心是可交互、玩法逻辑自洽、基本可玩。
- prompt 未写的通用游戏特性不强制。例如未要求多关卡、金币、商店等，不应直接因缺少这些判 -1。
- 对同类游戏的常规体验可作为功能缺陷参考，例如速度极不合理、控制失灵、碰撞/得分/重开逻辑不可用。
- 对游戏体验的痛点允许有一定理解差异，关键是理由要逻辑自洽、基于用户体验。
- Subway Surfer 类跑酷不必完全复刻地铁元素或金币玩法，若已有横向滚动、躲避障碍等核心玩法，可给 0 并提出改进。

## 动画场景判定

- 0515 更新：首轮标注时，-1 表示有功能缺陷、效果极差、基本不可用或不可玩；0 表示中规中矩，在 UI 或部分交互上存在问题；1 表示整体良好、基本没问题。
- 后续轮次以首轮为锚点：0 可表示中规中矩或与首轮相比无明确提升；1 要整体良好并有明确提升，允许存在瑕疵。
- 动画场景是动态场景，完全没有动效不行。
- 动画场景评语只指出存在的问题即可，不需要发散写期待效果。

## 易错点

- 不要在提交文案里提到版本、对比、基线、初始版、V0 或类似词。可以心里参考旧版本，但标注文案只描述当前产物现状。
- 不要直接在标注平台嵌入页看控制台，因为可能混入平台内容。必须新窗口打开产物再看控制台。
- 不要把 prompt 没要求的扩展功能写成不通过原因。
- 不要把所有 error 或 warning 都当作失败充分条件，仍需看实际体验和核心功能。
- 不要因为美观度个人偏好过度苛刻。第一批数据尽量客观，能看过去即可。
- 不要忽视 prompt 明确颜色、主题、动效、移动端、响应式等要求。
- 不要漏测自然控件。页面有按钮、tab、滑块、上传、重开、画笔、选择器时，应点击或操作验证。

## 理由话术

- 理由用自然中文，尽量短而具体，通常 30 字左右。
- 好的实现可以写出具体做得好的点。
- 有问题时先说明当前问题，再给出符合预期的逻辑或需要补充的内容。
- 不要出现版本、对比、基线、初始版、V0 等字眼。
- 白屏、ready to build、渲染报错等理由要带具体状态或报错摘要。
- 动画场景按 0515 更新，只指出存在问题即可，不需要展开期待效果。

## 问卷知识点

- 三档分值分别是 +1、0、-1。
- +1 不要求额外亮点，只要功能完整度、功能缺陷、美观度都通过即可。
- 功能完整度看 prompt 明确要求是否覆盖。
- 功能缺陷看已实现功能是否有 bug 或交互故障。
- 美观度看布局、样式、视觉观感，不要过度主观苛刻。
- 白屏、空白页、ready to build 不直接废弃，要新窗口打开并查看控制台报错。
- prompt 明确移动端友好或响应式时才强制检查移动端。
- 标注文案不能提版本、对比、基线、初始版或 V0。
- 动画场景完全没有动效不行。
- 游戏类未在 prompt 中提到的通用扩展功能，默认不作为不通过原因。
