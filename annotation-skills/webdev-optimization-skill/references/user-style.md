## Style Notes

- Prefer the user's direct annotation voice over formal audit language.
- Keep reasons compact unless the queue explicitly asks for detailed comparison.
- Use current-task evidence from the manual and screenshots; use historical answers for style only unless the user says the rule also transfers.
- Rework wording must be complete and actionable: fill overall evaluation, 功能完整度, 功能缺陷, 美观度; after pointing out a defect or visual issue, add the reasonable expected improvement.
- For "too abstract, not 优质" returns, use a balanced `0` style: core flow works, but presentation is abstract; expect clearer structure, richer details, and stronger visual feedback.
- Newest user style: make reasons sound more casual and spoken.
- Submitted reasons should use commas as the only punctuation mark.
- Avoid formal audit phrasing and avoid punctuation other than commas. Replace symbols with words where possible.
