## Style Patterns

- Use `能够...核心功能基本实现，可以正常游戏` for passable games.
- It is acceptable to mention partial implementation directly, e.g. `能够进行移动，能够实现破拆与建造元素，但是无法切换不同方块`.
- For opponent-controlled games, prefer `对手` over model-like words such as `AI` when writing reasons.
- In a batch, vary wording with `实现了`, `可以`, `能正常`, `点击后`, `页面有`, and `角色可以`; do not repeat `能够` for every reason.
- Use `无法...无法正常游戏` for broken games.
- Use `点击...无反应，无法...` for broken buttons or controls.
- Use `未实现...功能` when a named feature is missing.
- Use `页面...不完整/空白/未正常渲染` for rendering issues.
- Use `和参考图不符/存在明显不同` for visual comparison failures.
- Use `整体趋势一致/数据准确/无大问题` for chart pass reasons.
- For game wording, prefer generic names like `角色`, `人物`, `车辆`, `敌人`, `目标`, `碎片`, `障碍物`, and `关卡`; avoid copying special prompt names such as named heroes or themed creatures unless necessary.
